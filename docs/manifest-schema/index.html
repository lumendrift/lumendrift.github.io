Manifest schema

The complete shape of a UCP manifest, field by field.

Discovery location

Publish the manifest at /.well-known/ucp.json on the apex domain. Subdomains may publish their own manifest if they expose distinct capabilities.

Root fields

  • version — UCP protocol version (e.g. "1.0").
  • store — object: name, domain, platform.
  • capabilities — map of capability name to { endpoint, methods }.
  • identity — supported agent identity schemes (array).
  • payments — supported payment instruments.
  • contact.agent_relations — operator email for agent operators.

Reference example

ucp.json
 1{
 2  "version": "1.0",
 3  "store": {
 4    "name": "Example Store",
 5    "domain": "shop.example.com",
 6    "platform": "shopify"
 7  },
 8  "capabilities": {
 9    "catalog":  { "endpoint": "/api/ucp/catalog",  "methods": ["GET"] },
10    "search":   { "endpoint": "/api/ucp/search",   "methods": ["GET"] },
11    "cart":     { "endpoint": "/api/ucp/cart",     "methods": ["GET","POST","DELETE"] },
12    "checkout": { "endpoint": "/api/ucp/checkout", "methods": ["POST"] },
13    "order":    { "endpoint": "/api/ucp/orders/{id}", "methods": ["GET"] }
14  },
15  "identity": { "schemes": ["agent-token","mtls"] },
16  "payments": ["card","apple_pay","agent-wallet"],
17  "contact":  { "agent_relations": "agents@example.com" }
18}

Capability shapes

Each capability declares an endpoint (relative to the store domain) and the HTTPmethods the endpoint accepts. Capabilities are namespaced; future versions may introduce new capability names without breaking existing manifests.

Versioning

Always pin the version field. Agents use it to negotiate compatible feature sets.
